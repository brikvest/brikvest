# Brikvest - Real Estate Investment Platform

## Overview
Brikvest is a membership-based fractional real estate investment platform. It allows approved members to invest in properties with fractional ownership, starting from ₦30,000. The platform aims to provide exclusive property access to its members while adhering to SEC compliance. It features a dedicated investor interface and a comprehensive administrative dashboard for managing properties and members. The platform also includes a self-service portal for property developers to list and manage their projects, aiming to expand property offerings and cater to a broader market.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture
The application utilizes a modern full-stack architecture designed for scalability and maintainability.

**Frontend**: Developed with React, TypeScript, and Vite. It uses Wouter for routing, React Query for state management, shadcn/ui and Radix UI for UI components, TipTap for rich text editing, React Hook Form with Zod for form management, and Tailwind CSS for styling.

**Backend**: Implemented with an Express.js server in TypeScript, leveraging Drizzle ORM for PostgreSQL interactions. It uses Express session for admin authentication, `crypto` for password hashing, Multer with Cloudinary for image uploads, and Nodemailer with Gmail SMTP for email services.

**Database**: PostgreSQL is used as the primary data store, managed through Drizzle ORM.

**Authentication**: A dual authentication system is in place for general users and administrators. Access to investment features requires approved membership, which is granted by an administrator. Property listings and P2P marketplace listings are publicly viewable.

**File Storage**: Cloudinary is used for storing images, while Replit Object Storage handles PDF documents.

**Email Service**: Gmail SMTP is integrated for transactional emails and automated notifications.

**UI/UX Decisions**: The platform features a modern, responsive design with Tailwind CSS and shadcn/ui components, inspired by Stripe's user dashboards. It incorporates gradient designs for public-facing pages and is optimized for mobile-first responsiveness. Sensitive financial data in dashboards is blurred until KYC verification is complete. The public landing-page header is intentionally minimal — only essential primary links (Properties, Insights, About), a compact currency selector, a subtle "List your project" CTA, and either a "Sign in" button or an avatar `DropdownMenu` (My Portfolio / List your project / Sign out) — keeping the top bar uncluttered and professional.

**Key Features**:
- **Fractional Property Investment**: Enables investment in properties with fractional ownership.
- **Membership Management**: Admin approval for new members and comprehensive member management.
- **Property Management**: Detailed property listings, investment reservations, and robust admin tools for property management.
- **Financial Features**: Multi-currency support with real-time exchange rates, consistent currency conversion across the platform.
- **Market Insights**: Provides market data for specific locations with data visualization, derived from web scraping.
- **User Dashboard**: A comprehensive dashboard for investors to manage their investments and view performance.
- **KYC Verification**: A full Know Your Customer (KYC) system with document uploads for compliance.
- **Ownership Certificates**: Generation and verification of ownership certificates for confirmed investments.
- **Reservation System**: Automated 24-hour reservation expiration and a user-initiated payment submission workflow.
- **Property Valuation**: Admins can upload per-property valuation report PDFs. The system stores historical valuation records and renders two data-driven charts for investors: Land Appreciation and Investment Performance.
- **Referral Program**: Users receive a unique referral code with configurable reward tiers and tracking.
- **P2P Unit Resale System**: Allows approved investors to list their units for resale to other approved members. Features include fixed-price and bidding options, unit locking, admin review, and a dedicated marketplace.
- **Resale Anti-Abuse & Fallback**: Implements KYC gating, self-trade prevention, unit locking, anti-sniping, payment retry limits, and an expired payment deadline fallback system to ensure fair and secure transactions. An admin-controlled transfer process ensures integrity.
- **Resale Audit Trail**: A comprehensive logging system records every significant P2P resale action for dispute resolution, compliance, and reporting.
- **Co-Investor Notifications**: Co-investors in a property are notified via email when a unit in that property is listed for resale.
- **Developer-Recorded (Off-Platform) Investments**: Developers can record investors who paid them directly via the Sales tab → "Add investor" dialog (`AddInvestorDialog` in `client/src/pages/developer/project-detail.tsx`). The endpoint `POST /api/developer/projects/:id/investors` (in `server/routes.ts`) validates email/name/units, computes amount from `unitPrice||minInvestment` if omitted, checks remaining capacity (`totalUnits - reservedUnits - soldUnits`), looks up the user by email or creates a new approved/email-verified user with a randomly generated temporary password (hashed via `hashPassword`), creates a reservation with `status='converted_to_investment'` and a `DEV-YYYYMMDD-HEX` payment reference, bumps `properties.soldUnits` via `updatePropertyUnitCounts`, issues an ownership certificate via `getNextCertificateNumber()` + `createOwnershipCertificate()` (with required `ownerName`/`propertyName`/`propertyLocation`/`spvName` fields), and sends a branded email via the new `developerInvestmentRecordedEmailTemplate` in `server/emailTemplates.ts` containing the investment summary, certificate number, conditional new-account credentials block (email + temp password) or existing-account login CTA, and a "track your investment" link to `https://www.brikvest.net/login`. KYC gating is intentionally bypassed since the developer has already vetted and collected payment off-platform.
- **Developer Pricing Page**: Public marketing page at `/developer/pricing` (`client/src/pages/developer/pricing.tsx`) presenting two plans — **Starter** (₦50,000/mo or ₦480,000/yr) and **Growth** (₦150,000/mo or ₦1,440,000/yr, marked Most popular) — with a Monthly/Yearly billing toggle (yearly shows a "Save 20%" badge and divides the annual price by 12 for the displayed monthly figure), a "3 months free trial" hero badge, per-plan feature lists, FAQ accordion, and CTAs to `/developer/signup`. Linked from `developer/login.tsx` and `developer/signup.tsx`. Pricing is presentational only at this stage — no payment processing or trial enforcement yet.
- **Developer Plans, Trials & Team Seats**: Each developer account has a `plan` (`starter` | `growth`), a `subscriptionStatus` (`trialing` | `active` | `expired` | `cancelled`), and trial timestamps (`trialStartedAt` / `trialEndsAt`). New developer signups are auto-enrolled in a **3-month free trial** (90 days, defined as `TRIAL_DAYS` in `shared/plans.ts`). Plan caps live in `PLAN_LIMITS` (`shared/plans.ts`): **Starter** = 1 project / 10 investors / 1 update per month / 2 seats; **Growth** = 5 projects / 50 investors / unlimited updates / unlimited seats. Caps are enforced server-side in `server/routes.ts` on `POST /api/developer/projects`, `POST /api/developer/projects/:id/investors` (existing investors adding more units bypass the investor cap), and `POST /api/developer/projects/:id/updates`; over-limit requests return HTTP **402** with `code: plan_limit_projects | plan_limit_investors | plan_limit_updates | plan_limit_seats`. A `checkTrialActive(req, res)` helper returns HTTP 402 with `code: trial_expired` for any developer write once the trial elapses on a non-active subscription. The frontend parses these via `toastFromError()` in `client/src/lib/planErrors.ts`. **Team seats** are backed by `users.parentDeveloperId` + `users.teamRole` ('owner'/'member'), a new `developer_team_invites` table (token, email, status, 14-day expiry), and a per-feature `permissions` text array on both `users` and `developer_team_invites`. Owners invite teammates from `/developer/team` (page in `client/src/pages/developer/team.tsx`); invitees receive a branded `developerTeamInviteEmailTemplate` email (which lists granted access as chips) and complete signup at the public `/developer/accept-invite/:token` page (auto-login on success via `req.login`). Only owners can invite, revoke, remove members, edit permissions, or access billing operations (enforced via the `requireDeveloperOwner` middleware). **Per-feature permissions** for team members are defined in `shared/permissions.ts` with broad keys (`fundraising`, `construction`, `cap_table`, `sales`, `comms`, `settings`); the invite dialog and an "Edit access" dialog on each member row use a checkbox grid (`PermissionGrid`) for owners to grant access. Owners implicitly have all permissions; members get exactly what's granted. Server-side, a `requirePermission(key)` middleware in `server/routes.ts` gates the relevant write endpoints — `settings` for project create/edit/submit, `sales` for `/investors`, `/leads*`, and lead-convert, `construction` for milestones (POST/PATCH/DELETE/reorder), `comms` for `/updates` — returning HTTP 403 with `code: permission_denied`. The frontend hides whatever the member can't access: `DeveloperLayout` filters nav items (New Project, Communications) by required permission, and the project-detail page filters its tab strip (Fundraising/Construction/Sales/Cap Table/Comms) so members only see the tabs they're allowed in. `/api/developer/me` returns `permissions` and `isOwner` so the UI can render accordingly. A `PATCH /api/developer/team/members/:id/permissions` endpoint (owner only) lets owners update access at any time. `GET /api/developer/me` returns `plan`, `planLimits`, `usage`, `trialDaysRemaining`, and `isOwner` so `DeveloperLayout` can render a trial-countdown banner (blue ≤30 days, amber ≤7 days, rose on expiry) plus a "View plans" CTA linking to `/developer/pricing`.
- **Project Funding Model**: Every project captures how it's being funded so the right return/repayment terms surface to investors and the team. The new project wizard (`client/src/pages/developer/new-project.tsx`) has a dedicated **Funding model** step (step 2 of 5) with: a master "external investors?" toggle (off → `fundingTypes: ['self_funded']`, `acceptsExternalInvestors: false`); a **multi-select** card-picker of four investor-facing models — `equity` (co-ownership), `fixed_return` (committed ROI %), `profit_share` (% of net profit), `loan` (debt + interest, no ownership) — combinable in any mix (e.g. fixed return + equity upside replaces the old single "hybrid" option); conditional fields for return terms (`expectedReturnPercent`, `returnPeriod` ∈ annual/project_lifetime/quarterly/monthly, `investmentTermMonths`, `payoutFrequency` ∈ on_exit/lump_sum/monthly/quarterly/annually) shown when fixed_return or loan is selected; an `exitStrategy` selector (sale/land_appreciation/rental_income/buyback/refinance/other) shown when equity or profit_share is selected; and a free-form `fundingNotes` textarea for payment plans, milestones, or to spell out combined-model structures. Persisted on `properties` via columns `fundingTypes` (Postgres `text[]` with default `ARRAY['equity']`), `acceptsExternalInvestors`, `expectedReturnPercent`, `returnPeriod`, `investmentTermMonths`, `payoutFrequency`, `exitStrategy`, `fundingNotes` in `shared/schema.ts`. The project detail Overview tab renders a **Funding model card** that shows one badge per selected funding type, key metrics (return, term, payout, exit), and any funding notes. The POST `/api/developer/projects` handler in `server/routes.ts` accepts the `fundingTypes` array, defaulting to `['equity']` (or `['self_funded']` when external investors are off).
- **Structured Construction Schedule**: The developer project Construction tab (`client/src/pages/developer/project-detail.tsx`) is built around an **8-stage industry-standard schedule** — Site Preparation, Foundation, Structure, Roofing, MEP (Mechanical/Electrical/Plumbing), Finishes, Landscaping & External Works, Handover & Inspection — defined in `DEFAULT_CONSTRUCTION_STAGES` (`shared/schema.ts`) and persisted in the `construction_stages` table (one row per stage per property, seeded automatically on project create via `storage.seedDefaultConstructionStages`). Each stage tracks `plannedStartDate`, `plannedCompletionDate`, `actualStartDate`, `actualCompletionDate`, `status` (`not_started`/`in_progress`/`done`/`delayed`), and `notes`. The tab renders: a **Schedule card** with read-only project-level dates (`plannedStartDate` / `plannedCompletionDate` set in the new-project wizard step 1, plus a server-derived `actualCompletionDate` and planned duration in months); a **Completion progress card** showing `% complete = stages with actualCompletionDate ÷ 8` plus the next pending stage; a **Stages table** with 8 rows, each showing planned/actual date ranges, planned duration in days, status badge, and a **variance pill** (green for on-time/early or completed, amber for ≤7 days late/overdue, red for >7 days), plus a Pencil edit button per row; a CSS-based **Gantt timeline** (`ScheduleGantt` component) with light-blue planned bars and blue/emerald actual bars per stage and a vertical "today" reference line. Stage editing is gated server-side by the `construction` permission via `PATCH /api/developer/projects/:id/stages/:stageId` (`server/routes.ts`), which validates stage-project ownership, coerces date strings, auto-derives `status` from `actualCompletionDate` if not explicitly set, and recomputes the project's `actualCompletionDate` as the max of stage actuals (or null) on every save. `GET /api/developer/projects/:id/stages` idempotently re-seeds the 8 default rows for legacy projects. The **legacy free-form milestones** UI (project status fields + drag-reorderable milestone list with photos) is preserved in a collapsed `Accordion` "Detailed milestones" below the schedule, since it's still used by the public investor dashboard.
- **Developer Portal**: A self-service portal for property developers to list, manage, and communicate about their projects. The portal uses a fully responsive shell (`DeveloperLayout`) — fixed sidebar on desktop (≥`lg`), slide-over drawer (shadcn `Sheet`) with hamburger trigger on mobile/tablet, sticky `backdrop-blur` top bar, and a user `DropdownMenu` (profile + sign out) accessible from both the desktop sidebar footer and the mobile top bar avatar. **Project detail URLs use a human-readable slug (`/developer/projects/lekki-heights-off-plan`) instead of the numeric id; the slug is generated client-side via `slugify()` in `client/src/lib/utils.ts`, and a small server helper `resolveDevProjectId(req, res)` in `server/routes.ts` (called inside every `/api/developer/projects/:id*` handler) accepts either the numeric id or a name slug, looking it up against the requesting developer's own projects.** **The project detail page tab bar is responsive: a Select dropdown collapses the six tabs (Overview / Funding / Build / Cap / Comms — Sales is wider) on `<md` viewports and an equal-width 6-col `TabsList` is used on `md+`.** Includes project creation (draft, pending approval, live), an explicit **sales lifecycle stage** (`off_plan` | `completed`) toggleable from the Sales tab and surfaced as a badge on project cards, construction milestone tracking with drag-and-drop reordering (single bulk `POST /api/developer/projects/:id/milestones/reorder` endpoint, optimistic UI via `@dnd-kit/sortable`) and per-milestone progress photos with drag-to-reorder thumbnail strip in the milestone dialog (saved via the existing PATCH `mediaUrls` array, no new endpoint), sales analytics (stage-filtered investor list, 4-week velocity, sell-out forecast, sales-velocity chart), **multi-currency fundraising rollups (NGN/USD/GBP equivalents) for both list and per-project rollup endpoints**, **CRM-style pre-reservation Leads sub-section on the Sales tab** backed by a `developer_leads` table (stages: `lead`/`contacted`/`qualified`/`converted`/`lost`) with stage filter chips, manual lead capture, in-line stage editing, one-click conversion to a soft-locked reservation, and a sell-out forecast that factors in qualified-lead pipeline using historical qualified→converted conversion rate, investor updates with email broadcast, communications history, profile management, and private investor notes. A demo seed (`scripts/seed-demo-developer.ts`, run with `npx tsx scripts/seed-demo-developer.ts`) provisions a demo developer with two showcase projects — **"Lekki Heights — Off-Plan"** at ~62% funded and **"Maitama Garden Villas — Completed"** at ~91% funded — six milestones each, six to seven confirmed investors per project (back-dated for realistic velocity charts), and three project updates each. The seed is fully idempotent: re-running it converges existing reservations and milestones to the seed-defined state.
- **Fundraising Analytics (Developer Project)**: The Fundraising tab on a developer project (`client/src/pages/developer/project-detail.tsx`) renders three data-driven charts powered by an extended `/api/developer/projects/:id/rollup` endpoint in `server/routes.ts`: (1) a **Fundraising velocity** recharts `AreaChart` showing cumulative ₦ raised over the last 12 weeks (currency-converted to the project currency via `convertCurrency`), with an optional dashed `ReferenceLine` for the weekly target needed to hit `plannedCompletionDate`; (2) a 5-stage **Conversion funnel** (Prospective → Due Diligence → Documentation → Payment Incomplete → Confirmed) rendered as a custom descending bar with per-stage drop-off %, driven by the new `funnel_stage` column on `investment_reservations` via the `getReservationFunnelCounts` storage helper; (3) an **Investor Conversion Efficiency** monthly line chart (recharts `LineChart`, last 12 months, % Y-axis, tooltip shows `confirmed/total`) backed by the `getMonthlyConversionEfficiency` helper. Each chart has a friendly empty state ("No prospective investors yet — share your project link to start tracking conversion"). The investor list shows an inline `<Select>` for non-terminal rows that PATCHes `funnelStage` via the new `PATCH /api/developer/reservations/:id/stage` endpoint (gated by the `sales` permission via `requirePermission("sales")`, validates against `RESERVATION_FUNNEL_STAGES`, scoped to the requesting developer's own projects). User-facing "Reservation"/"Reservations" labels in the developer portal Overview, stat cards, investor table, drill-down dialog, and Leads section read as "Prospective Investor(s)" — internal DB statuses, route paths, and query keys are unchanged.
- **Data Integrity**: Safeguards include linking orphaned reservations, unique constraints for referral codes, and audit logging for critical actions.
